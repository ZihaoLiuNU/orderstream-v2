# OrderStream 压测报告

> 测试日期：2026-09-25
> 环境：单机 Docker Compose（10 个容器：7 应用 + Postgres + Redis + Kafka）
> 压测工具：k6（容器内运行，与被测系统同网络，排除公网抖动）

---

## 一、先说清楚测的是什么

**"500+ concurrent order events"** 有两种解读，必须先把口径讲明白，否则数字没有意义。

| 解读 | 含义 | 本系统的真实情况 |
|---|---|---|
| ❌ "500 TPS" | 每秒处理 500 单 | **做不到**。异步链路上限约 120 单/秒，由 payment-service 决定 |
| ✅ "500 并发在途订单" | 同时承载 500 个并发用户下单且不降级 | **做到了**，p95 = 229ms，零错误，零数据丢失 |

**本报告采用第二种口径**，并且同时给出：
1. 同步下单接口在不同并发下的延迟曲线（用户能感知的部分）
2. 异步 Saga 链路的吞吐上限及其瓶颈定位
3. **压测后的数据正确性验证**（这一项比前两项更重要）

---

## 二、容量曲线

场景：ramping-vus，20s 预热 → 30s 爬升 → 60s 稳态 → 20s 收尾。
每个 VU 下单后 sleep 1~3 秒模拟真实用户思考时间。
餐厅和菜品随机选取，避免热点行导致的失真。

| 并发 (VU) | 创建订单数 | p50 | p95 | p99 | max | 吞吐 | 错误率 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 | 5,523 | 16.1 ms | 25.5 ms | 37.1 ms | 86.7 ms | 39.9 /s | 0.00% |
| 200 | 9,760 | 17.6 ms | 45.2 ms | 78.3 ms | 186.7 ms | 68.3 /s | 0.00% |
| 300 | 14,168 | 16.7 ms | 32.4 ms | 59.4 ms | 120.4 ms | 98.6 /s | 0.00% |
| **400** | 18,322 | **16.2 ms** | **26.1 ms** | 55.2 ms | 171.1 ms | 119.9 /s | 0.00% |
| **500** | 22,147 | 35.7 ms | **228.6 ms** | 605.0 ms | 1,275.7 ms | **144.0 /s** | **0.00%** |

### 怎么读这张表

- **拐点在 400 VU 附近**：到 400 并发为止，p95 稳定在 30ms 以内，延迟几乎不随并发增长 —— 说明系统还远没到饱和。
- **500 VU 时开始排队**：p95 从 26ms 涨到 229ms（约 9 倍），但 **错误率仍然是 0**。
  这正是我们想要的降级形态：**请求变慢，但不失败、不丢数据**。
  如果这里出现的是大量 5xx 或超时，那才是设计有问题。
- **吞吐随并发单调上升到 144 req/s 才开始出现排队**，说明瓶颈不是锁竞争（那会导致吞吐下降），而是资源饱和。

## 三、异步链路的吞吐与瓶颈

同步接口只负责"订单落库"。真正的处理（库存预留 → 支付 → 确认）在 Kafka 后面异步完成。

压测结束后观察 Saga 积压的排空速率：

```
进行中 Saga: 9986 → 8389 → 6819 → 5229 → 3645 → 2071 → 536 → 0
（每 15 秒采样一次）
```

**排空速率约 107 单/秒**。

### 瓶颈定位：payment-service

这个数字不是猜的，可以直接算出来：

```
payment-service 的消费并发度 = 6（consumer-concurrency，受 topic 6 分区限制）
单笔支付的模拟延迟       = 50ms
理论上限 = 6 / 0.05 = 120 单/秒
```

实测 107 与理论 120 吻合（差值来自 GC、DB 往返等开销）。

**瓶颈是模拟的支付网关延迟，不是订单服务本身。** 要提升只有三条路：

1. 加 topic 分区 + 提高 consumer-concurrency（单实例内的并行度）
2. 加 payment-service 实例（Kafka 自动重新分配分区，水平扩展）
3. 降低单笔支付耗时（真实环境下这取决于支付网关，我们控制不了）

第 2 条是微服务架构真正的价值所在：**瓶颈服务可以单独扩容，不需要连带扩容整个系统**。

## 四、数据正确性验证（最重要的部分）

> 一个分布式系统"跑得快"是廉价的 —— 丢消息、超卖、重复扣款都能让 TPS 很好看。
> 难的是**又快又对**。

累计 **90,136 笔订单**（5 轮压测叠加）跑完后的全量校验：

```
==================== 总量 ====================
  订单数          : 90136
  Saga 数         : 90136
  支付记录数      : 90136
  库存预留记录数  : 90136
  PASS  订单数 == Saga 数（同事务创建）

==================== 1. 没有卡死的 Saga ====================
  PASS  没有 Saga 停留在进行中状态
  PASS  没有 FAILED 状态的 Saga
  COMPLETED(成功): 81163   COMPENSATED(已补偿): 8973
  补偿率约 9% —— 与配置的 10% 模拟支付失败率吻合

==================== 2. 没有丢失的事件 ====================
  PASS  order_db 的 outbox 无积压
  PASS  payment_db 的 outbox 无积压
  PASS  menu_db 的 outbox 无积压

==================== 3. 没有重复扣款 ====================
  PASS  没有重复的支付幂等键
  PASS  同一订单没有多笔支付
  PASS  成功订单总额 == 成功支付总额（跨库对账）  1,866,713.58

==================== 4. 库存守恒 ====================
  初始库存 50,000,000 = 当前剩余 49,916,955 + 预留占用 83,045
  PASS  库存守恒（单快照测量）
  PASS  逐个菜品对账均无偏差（排除互相抵消）
  PASS  没有负库存（无超卖）
  已释放的预留（补偿执行次数）: 48,623

==================== 5. Saga 与订单状态一致 ====================
  PASS  Saga 状态与订单状态完全一致
  PASS  所有取消的订单都有原因

==================== 6. 死信队列 ====================
  PASS  所有死信队列为空（没有消息被丢弃）

结果：通过 15 / 失败 0
```

### 这些数字里最值得看的三条

1. **90,136 : 90,136 : 90,136 : 90,136** —— 订单、Saga、支付、库存预留四者精确 1:1:1:1。
   任何一个数字对不上，都意味着某个环节丢了消息或重复处理了。

2. **跨库对账分毫不差**：`1,866,713.58` 是 order_db 里所有成功订单的总额，
   也是 payment_db 里所有成功支付的总额。两个**物理上独立的数据库**，
   没有外键、没有分布式事务，靠 Saga + Outbox + 幂等达成最终一致。

3. **库存精确守恒到个位**：50,000,000 = 49,916,955 + 83,045。
   4.8 万次补偿（释放库存）执行下来，没有多还一份，也没有少还一份。

## 五、压测过程中发现并修复的 4 个真实问题

> 这一节比上面的数字更有价值 —— 这些问题**只有真正跑起来才会暴露**。

### 1. Outbox relay 是吞吐瓶颈（提升 40 倍）

**现象**：压测产生 64,737 条待发事件，排空速率只有约 **30 条/秒**，要跑 35 分钟。

**根因**：relay 在循环里逐条 `send().get()`，把 100 条消息变成了 100 次串行的网络往返。
在 `acks=all` 下每次往返 10~20ms，一批就要 1~2 秒。

**修复**：改成**整批先全部发出，再统一等待 ack**。
利用 producer 的 `linger.ms=10` 自动合并，往返次数从 100 降到几次。

**结果**：**30 条/秒 → 约 1,400 条/秒**。3 万条积压 35 秒排空。

关键是**没有牺牲可靠性**：依然在标记 `sent_at` 之前确认了每一条的 ack。
做的是"消除串行等待"，不是"取消等待"。

### 2. `@Scheduled` 默认只有 1 个线程，导致 relay 被完全饿死

**现象**：修完上面那条之后，relay 依然**完全不工作**，5 万条积压纹丝不动，
`attempt_count` 全是 0（说明根本没被尝试过）。

**根因**：Spring Boot 的 `TaskScheduler` **默认 pool size = 1**。
`StuckSagaSweeper` 一次性加载 3 万个卡死的 Saga 在一个事务里逐个补偿，
单次执行 3 分半。这期间 `OutboxRelay` **一次都没被调度**。

表现出来像"Outbox 坏了"，实际是"Outbox 根本没机会运行"。排查方向完全被带偏。

**修复**：
- `spring.task.scheduling.pool.size: 5`
- 兜底扫描器加 `LIMIT 500`，每轮限量处理
- 每条补偿改为**独立事务**（`REQUIRES_NEW` + 独立 Bean）

### 3. 事务里 catch 异常是无效的

兜底扫描器原来在一个大事务里循环，`catch` 住单条异常继续跑。
这在 Spring 里**不起作用**：repository 抛出的 RuntimeException 已经把事务标记为
rollback-only，后面的循环全是白干，最终提交时抛 `UnexpectedRollbackException`，
**3 分半的工作全部回滚，一条都没成功**，60 秒后从头再来，永远跑不完。

要让"一条失败不影响其他条"，必须让每条各自在**独立事务**里 —— 而这又踩到了
**Spring AOP 自调用**陷阱（同类内调用不经过代理，`REQUIRES_NEW` 静默失效），
所以补偿逻辑被拆成了独立的 `StuckSagaCompensator` Bean。

### 4. Alpine 镜像的 musl libc 与 snappy 原生库不兼容

Kafka producer 持续报 `NoClassDefFoundError: org.xerial.snappy.Snappy`。
根因是 Alpine 用 musl libc，而 snappy-java 打包的 `.so` 是针对 glibc 编译的。

**这个故障顺带演示了 Outbox 模式的价值**：
消息通道中断了约 20 分钟、单条事件重试 **309 次**，
修好基础镜像后 relay **自动补发，订单完整走完 Saga，零数据丢失**。

如果当初是"直接 `kafkaTemplate.send()`"，这 20 分钟的订单全部静默丢失，
而且没有任何痕迹可供恢复。

## 六、测试方法论上踩的两个坑

> 写下来是因为它们会让人**误判系统有 bug**，浪费大量排查时间。

### 坑 1：清空数据库 ≠ 清空系统状态

只 TRUNCATE 了 5 个数据库就重跑压测，结果校验报出：
**订单 17,893 条，但支付记录 31,904 条**。

原因：Kafka 里还积压着上一轮的三万多条消息，它们在截断之后才被消费，
为一批**已经不存在的订单**创建了支付记录。

**在事件驱动系统里，状态不只在数据库，还在消息队列的未消费消息和消费者 offset 里。**
重置环境必须三者一起处理（见 `reset.sh`）。

### 坑 2：守恒类不变量不能用多条查询验证

报出 91 个单位的"库存泄漏"，差点去查代码。
但逐个菜品对账**全部为 0**。

原因：验证脚本分两次查询（先查剩余库存、再查预留量），
两次之间隔了几十毫秒，而后台兜底任务仍在释放库存。
**两个不同时刻的快照相减，当然对不上。**

修复：把两个聚合放进**一条 SQL**（Postgres 的 MVCC 保证单语句看到一致快照）。

教训：任何"偶发的、量很小的不一致"，**先怀疑测量方法，再怀疑系统**。

## 七、可复现步骤

```bash
# 1. 启动
cp .env.example .env          # 并填入 JWT_SECRET（openssl rand -base64 48）
docker compose up -d --build

# 2. 端到端冒烟（16 项，含安全与 Saga 全流程）
bash loadtest/smoke-test.sh

# 3. 重置到干净状态（数据库 + Kafka topic + Redis 一起清）
bash loadtest/reset.sh

# 4. 放开限流以测量真实容量，然后压测
RL_AUTH_RATE=200 RL_AUTH_BURST=400 RL_ORDER_RATE=1000 RL_ORDER_BURST=2000 \
  docker compose up -d --force-recreate api-gateway

docker run --rm --network=orderstream-v2_default -v "$PWD/loadtest:/scripts" \
  -e GATEWAY=http://api-gateway:8080 -e TARGET_VUS=500 -e USER_POOL=500 \
  grafana/k6 run /scripts/order-load-test.js

# 5. 等异步链路排空后，验证数据正确性
bash loadtest/verify-correctness.sh
```

> 关于第 4 步放开限流：**压测的目的是测出系统容量，不是测出限流器的阈值**。
> 正确顺序永远是「先测容量，再按容量设限流」，反过来做的话
> 你永远不知道自己离悬崖还有多远。
> 生产默认值（下单 10/s/用户）保留在 `application.yml` 里。

## 八、诚实的局限

| 局限 | 说明 |
|---|---|
| 单机环境 | 10 个容器挤在一台开发机上，CPU/内存/磁盘全部共享。真实部署下各服务独立，数字会明显更好 |
| 单 broker / 单副本 | 生产需要 3 副本 + `min.insync.replicas=2`，那会增加写入延迟 |
| 支付是模拟的 | 50ms 固定延迟。真实支付网关是 200~500ms 且会抖动，异步链路吞吐会相应下降到约 20 单/秒/实例 |
| 未测故障注入 | 没有测「Kafka 挂掉」「某服务被 kill」时的表现。不过 Alpine 那次事故意外地充当了一次真实的故障演练（消息通道中断 20 分钟，零丢失） |
| 数据量偏小 | 50 个菜品、1000 个用户。索引效果在千万级数据上才能充分体现 |
